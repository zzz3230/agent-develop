# Разнообразные задания для проверки агента

64 отдельные задачи: **по 16 на math, data_analysis, search и coding**. Здесь нет серии из пяти одинаковых задач с заменёнными числами. Это отдельная версия набора; результаты прежнего `benchmark100` к ней не относятся.

Этот набор помогает находить слабые места и сравнивать изменения. Он **не предсказывает результат конкурса**. Сложность пока оценена человеком; мы не запускали модели, чтобы подобрать удобные задания или получить заданный процент успеха. Ожидание организаторов «решат около 30%» не превращено в искусственную цель этого набора.

## Какой набор запускать

| Выборка | Задач | Когда использовать |
|---|---:|---|
| `smoke` | 12, по 3 каждого типа | Быстро проверить изменение: простые задачи, несколько составных и краевые случаи |
| `dev` | 40, по 10 каждого типа | Подбирать промпты, инструменты и ограничения |
| `holdout` | 24, по 6 каждого типа | Сравнивать уже выбранные версии; не подбирать параметры по этим результатам |
| `all` | 64 | Полная диагностика и выпускная проверка |

`smoke` входит в `dev`; `dev` и `holdout` не пересекаются. Повторные варианты одной задачи не разделены между выборками: каждая задача имеет собственную спецификацию. Общие алгоритмические идеи могут встречаться в разных типах — это не гарантия статистической независимости. Контрольная выборка открыта команде в Git, поэтому это дисциплина эксперимента, а не секретный набор организаторов. Если начали исправлять агент под конкретные ошибки контрольной выборки, она стала частью разработки: для следующего честного сравнения нужны новые задачи.

[Каталог всех заданий](CATALOG.md) содержит названия и предварительную сложность. Условия на английском, как в объявленных условиях конкурса.

## Что различается между задачами

- Математика: единицы, тарифы и округление, рабочий календарь, остатки от деления, вероятность, ограниченное число монет, геометрия, интервалы, назначения, математическое ожидание, множества, пути с препятствиями, кредит, одноразовая скидка на маршруте, распределение ресурсов.
- Данные: фильтры, снимки состояния, соединение по дате, когорты, кавычки и переносы в CSV, часовые пояса, пропуски, вложенный JSONL, сессии, скользящие окна, TSV и перцентили, отсутствующие связи, ревизии, дерево, последовательные операции. Размеры различаются: от коротких неоднозначных таблиц до сотен записей.
- Поиск: тёзки, переименования, дата публикации против даты действия, приоритет источников, несколько условий, числовые версии, цепочки связей, исключения к правилам, порядок событий, вложенные каталоги с 181 документом, markdown-таблицы, отменённые события, подсчёт уникальных сущностей, связь JSON с текстом.
- Код: коллекции, декодирование, интервалы, CSV, двоичный поиск, вложенные структуры, зависимости и циклы, сроки хранения, Decimal, кратчайшие пути, неровные таблицы, арифметический парсер, экранирование, редакционное расстояние, атомарные переводы, версии.

60 задач разрешимы. Ещё в четырёх нельзя однозначно восстановить ответ: неизвестные начисления, неоднозначный ключ соединения, равноправные противоречащие источники и отсутствующий биографический факт. Они не размечены как невыполнимые во входных данных. Отказ не даёт баллов. Их доля здесь 6.25%, **ниже объявленного ориентира конкурса 15–25%**; этот набор в первую очередь проверяет качество решения. Отдельно проверять планировщик на конкурсном составе всё ещё нужно.

`reward` меняется независимо от предварительной сложности; по нему нельзя надёжно угадывать трудность. Условия не предписывают инструмент, алгоритм, краткость ответа модели или экономию токенов. Требования к формату ответа, округлению, поведению функций и неизменности тестов — часть задачи. Для кода указан запуск публичных тестов, как в официальных примерах.

## Где входы, ответы и проверки

```text
input/dNNN/task.json          условие, тип, reward, check; без expected
input/dNNN/...                данные или сломанная программа и публичные тесты
references/dNNN/answer.json   ответ и объяснение для проверяющего
references/dNNN/solution.py   эталонное исправление кода
references/dNNN/test_private.py  дополнительные проверки кода
manifest.json                состав, разделение, SHA256 и служебные метки
build.py                     воспроизводимая сборка заданий без LLM
suite.py                     подготовка копий, валидация, оценка
```

**В контейнер агента монтируется только подготовленный каталог `tasks`.** Нельзя монтировать весь репозиторий или всю папку набора: там лежат ответы. `benchmarks/` также исключён из Docker build context. Эталоны и признаки `solvable`/сложности не должны попадать в запрос модели, схему CSV, индекс поиска или инструменты агента.

В этой версии файлы данных находятся рядом с `task.json`, без дополнительного `workspace`. В условии сохранена запись `answer.txt` рядом с `task.json`. Агент полного цикла должен сам обеспечить этот файл. Наш существующий M2-адаптер убирает завершающую инструкцию и записывает ответ за модель; это свойство адаптера, а не изменение заданий. Сравнение через `evaluation/compare_stock.py` нужно называть **сравнением решателей с общим адаптером**, а не проверкой полного конкурсного контура OJ.

## Быстрый старт

Команды выполняются из корня репозитория. Подготовка и валидация требуют только Python 3.10+ и стандартную библиотеку. Они не вызывают модели и не расходуют токены.

```powershell
python benchmarks/diverse-v1/suite.py validate
python benchmarks/diverse-v1/suite.py prepare --split smoke --out benchmark-runs/ours-01
```

`prepare` откажется перезаписывать существующий каталог. Для следующего прогона используйте новое имя. Получится `benchmark-runs/ours-01/tasks` с чистыми входами и отдельный `selection.json`, который остаётся у проверяющего. `benchmark-runs/` исключён из Git.

Далее запускайте нужного агента на этой копии. Например, для **нашего полного контура** в PowerShell, если образ `hack:latest` уже собран, а `LLM_BASE_URL` и `LLM_API_KEY` установлены в окружении:

```powershell
$caseDir = (Resolve-Path benchmark-runs/ours-01/tasks).Path
docker run --rm --env LLM_BASE_URL --env LLM_API_KEY --mount "type=bind,source=$caseDir,target=/data/tasks" --read-only --tmpfs /tmp:rw,size=2g --env HOME=/tmp --cap-drop ALL --security-opt no-new-privileges --cpus 8 --memory 16g --pids-limit 512 --workdir /app --entrypoint python hack:latest /app/run_agent.py --tasks-dir /data/tasks
python benchmarks/diverse-v1/suite.py grade --run benchmark-runs/ours-01 --image hack:latest
```

Это пример команды для ручного запуска, **не автоматический запуск при подготовке набора**. Сеть до прокси задаётся так же, как в вашей рабочей среде; при необходимости добавьте её `--network`. Образ проверяющего должен уже существовать локально: `grade` ничего не скачивает.

`grade` читает `answer.txt`, проверяет числа/строки и запускает исходные публичные плюс дополнительные тесты кода в отдельном Docker-контейнере без сети. Сохраняет `graded.json`: баллы, максимум баллов, число верных решений, результаты по типам и предварительной сложности. Неверный ответ и отсутствие ответа дают ноль. Неразрешимая задача не приносит баллов даже за `IMPOSSIBLE`. Показатель `abstentions_on_unavailable` включает пустой ответ; он не доказывает, что агент осознанно распознал нехватку данных.

Для строк местная проверка сводит пробельные последовательности к одному пробелу и игнорирует регистр. Для `exact_int` нужен один целочисленный ответ. Для кода требуется `DONE` и прохождение тестов; редактирование предоставленных тестов считается неуспехом. Точный нормализатор организаторов пока неизвестен — это явно зафиксированное местное соглашение.

Если используете `compare_stock.py`, передайте ему подготовленный `tasks` как `--input`, а результаты пишите в отдельный каталог. После прогона можно оценить его рабочие копии:

```powershell
python benchmarks/diverse-v1/suite.py grade --run benchmark-runs/ours-01 --submissions benchmark-runs/ours-01/output/tasks --usage benchmark-runs/ours-01/output/usage.jsonl --image hack:latest
```

`--usage` принимает JSONL нашего `Journal`. Тогда в отчёт входит стоимость **всех** зарегистрированных вызовов, включая прерванные задачи: вход / 10 + выход. Без файла usage стоимость будет `null`, а не выдуманный ноль. Для журнала другого формата сначала нужен явный конвертер. Reasoning уже входит в выходные токены, второй раз его не прибавляем. Для полного контура выше журнал `/tmp/harness/trajectory.jsonl` нужно отдельно сохранить до удаления контейнера; приведённая короткая команда сохраняет только ответы.

## Как сравнивать изменения честно и недорого

1. Сначала запускаем `smoke`. На этом этапе ищем поломки, а не объявляем победителя по 12 примерам.
2. На `dev` сравниваем по одному изменению: модель, инструмент, промпт или лимит. Обеим версиям даём свежие копии одинаковых задач, одинаковые ресурсы и зафиксированные настройки. Разные параметры являются частью сравниваемого агента и указываются в отчёте.
3. Для перспективной пары делаем 3 повторения на `dev`. Смотрим баллы, число верных ответов, общий расход, расход на задачу и время. После этого фиксируем версии.
4. На `holdout` делаем по 3 прогона уже выбранных версий. Отчёт показывает каждый прогон и диапазон, а не только лучший результат. Это практический минимум, не гарантия статистической значимости. 10–20 повторений каждой из 64 задач сразу слишком дорого; дополнительные повторы разумнее направить на случаи, меняющие выбор версии.
5. Для сравнения под общим бюджетом используем одну и ту же перестановку и реальный лимит прокси. Например, `prepare --split holdout --order-seed 101 --out ...`; следующие повторы — 102 и 103. `task_id` сохраняется, порядок каталогов меняется. Срез по сумме уже завершённых задач не равен настоящей остановке прокси посреди задачи.

Фиксируйте commit агента, образ, модель, параметры генерации, инструменты, все ограничения, SHA256 набора, seed порядка, время и журнал usage. При отсутствии измерения нельзя утверждать, что новая версия экономнее или решает больше. Не сравнивайте напрямую баллы `dev`, `holdout` и старого набора: состав разный.

## Изменения набора и ограничения проверки

`python benchmarks/diverse-v1/build.py` воспроизводит текущие файлы. `validate` проверяет их побайтовое соответствие источнику, состав выборок, отсутствие эталонов во входах, все эталонные программы и то, что исходные программы действительно не проходят публичные тесты. Дополнительные тесты содержат пустые входы, границы, неверные аргументы, повторения, неизменность входных данных и детерминированные случайные случаи. Для части алгоритмов проверка использует другой метод: например, перебор вместо выбора порядка, Bellman–Ford вместо Dijkstra, рекурсию вместо табличного расстояния.

Публичные тесты не являются полным контрактом; он написан в условии. Дополнительные тесты тоже не доказывают корректность для всех возможных входов. Docker изолирует выполнение от сети и файлов хоста; Python unittest не защищает от намеренной подмены тестовой системы в самой программе. Это проверка инженерного качества, не соревнование по взлому проверяющего.

В задачах на код явно требуется держать реализацию в `solution.py` и использовать стандартную библиотеку. Проверяющий переносит только этот файл, возвращает исходные публичные тесты и добавляет дополнительные. Это ограничение этих конкретных задач, а не утверждение об ограничениях всего конкурса.

Сам проверяющий можно проверить без моделей, если есть локальный Docker-образ с Python:

```powershell
python benchmarks/diverse-v1/check_pipeline.py --image hack:latest
```

Проверка прогоняет все эталоны, затем проверяет отклонение неверных ответов, испорченных тестов и реализации только под видимый пример. Она также проверяет выгрузку в перемешанном порядке и учёт стоимости незавершённой задачи. Сбой Docker останавливает оценку, а не выдаётся за неверный ответ агента.

Эталоны математики и данных имеют объяснение в `answer.json`, часть вычисляется при сборке перебором, точной арифметикой или двумя методами. Для текстового поиска указан источник и связь, определяющая ответ. Если обнаружена ошибка или неоднозначность, не подправляем файл молча после сравнения: выпускаем исправленную версию набора, фиксируем новый hash и повторяем затронутые измерения обеих версий агента.
