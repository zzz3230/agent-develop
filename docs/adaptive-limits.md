# Бюджет прокси и продление продуктивных попыток

Актуализация 11 ноября после уточнения команды. **Общий бюджет контролирует
прокси.** Локальные 100000 и переменная BUDGET — оценка для журналирования
и будущего планировщика. `Budget.check()` по умолчанию не блокирует вызов
из-за общей суммы, `run()` не останавливается по remaining()==0.
Ограничение всей серии остаётся у времени, окончания задач и отказов API.
Четыре последовательные необработанные ошибки API по-прежнему завершают
прогон. Это защита от неработающего сервиса, а не локальный токенный предел.

`enforce_total=True` существует только для явно ограниченных офлайн/benchmark
экспериментов. Конкурсный entrypoint его не включает. Нативный тест с
локальной оценкой бюджета 1 подтвердил выполнение нескольких запросов
с расходом выше этой оценки. Отдельно unit-тест продолжает run при
локальном счётчике больше 100000.

## Лимит отдельной задачи

Стартовый лимит разрешает попробовать решение. Перед следующим запросом
штатный BEFORE_MODEL_CALL hook проверяет шаги, расход и время. Если
достигнут один из стартовых пределов, а есть новый наблюдаемый прогресс,
лимиты увеличиваются. Достигнутый потолок или отсутствие прогресса
завершают только эту задачу. Продолжается та же сессия OJ.

| Тип | Шаги: старт → потолок | Расход: старт → потолок | Прибавка за продление | Продлений максимум |
| --- | ---: | ---: | --- | ---: |
| math | 3 → 6 | 700 → 2500 | +2 шага, +900 | 2 |
| data_analysis | 3 → 12 | 900 → 4500 | +3 шага, +1200 | 3 |
| search | 4 → 13 | 800 → 3500 | +3 шага, +900 | 3 |
| coding | 5 → 14 | 1500 → 6000 | +3 шага, +1500 | 3 |

Время: math 45→120 с, CSV 45→180 с, search 45→150 с, coding 60→240 с.
При продлении прибавляется до 45 с (coding — 60 с). Потолок времени
также ограничен остатком общего времени запуска. Максимальный вывод
на запрос: math/CSV 1200, search 900, coding 1600. Команда bash — до 30 с.
Это начальные параметры для проверки, не обученная оптимальная политика.
Стоимость остаётся мягким пределом: запрос может пересечь его; приращение
не разрешает следующий запрос, если расход уже выше нового предела.

Сигналы прогресса:
- coding: уменьшилось число failures/errors видимых unittest либо тесты прошли;
- search: получен новый непустой содержательный фрагмент чтением/поиском;
- вычисления: получен новый скаляр или промежуточный итог/число обработанных строк.

Одна правка файла не даёт продления. Повторённый вывод не считается новой
информацией. Оценка сложности самой моделью не запрашивается. Наблюдаемое
свидетельство расходуется при продлении; для следующего требуется новое.
Это эвристики: прочитанный фрагмент и промежуточное число не доказывают
близость к правильному ответу. Потолок и число продлений ограничивают риск.
Три одинаковые ошибки без изменения исходников всё ещё останавливают цикл.

## Ориентир организаторов: около 30% решённых задач

Это не означает, что остальные 70% логически невыполнимы. По правилам
невыполнимых ориентировочно 15–25%; остальные могут быть слишком дорогими
или трудными для нашего агента при бюджете. 100000 / 30 ≈ 3333 на один
полученный результат, **включая расходы на неудачные попытки**.

Начальные лимиты не резервируются и не списываются заранее. Продление
дорогой задачи должно в будущем сравниваться с альтернативами очереди по
reward × дополнительная вероятность успеха / дополнительная стоимость.
Сейчас очередь М3 ещё не реализована: драйвер по-прежнему идёт по каталогам,
а локальный контроллер использует только прогресс и профиль. М3 может
передавать AttemptLimits с другими стартами, потолками и числом продлений.
remaining() — ориентир; достижение нуля в локальной оценке не должно
становиться самостоятельной причиной завершения конкурсного запуска.

## Сколько проверок есть

- 31 отдельное условие в evaluation/fixtures/tasks: 29 выполнимых и 2 без
  достаточных данных. Это 8 официальных, 8 сложных разработческих,
  8 новых контрольных и 5 дополнительных экспериментальных условий.
- Основная регрессия — прежние 26: 24 выполнимых + 2 без данных.
- 16 автоматических unit/regression тестов (было 13 до этой правки).
- Настоящий ReActAgent с mock API: повторная ошибка, выход за локальную
  общую оценку, два продления одной сессии, мягкая остановка задачи и
  отдельный жёстко ограниченный benchmark-режим.

Повторы одних условий не увеличивают число разных задач. Этот корпус
не воспроизводит финальную сложность или распределение 15–25% невыполнимых.
Для обучения оценок и выбора глобальной политики нужны новые разнообразные
задачи, разделение по шаблонам и проверка на смешанных сериях с общим бюджетом.
