# Идеи

Предложения, которые ещё не проверены. Идея переходит в код после замера: по правилу проекта сравниваем сумму баллов при одинаковом бюджете, при равенстве — расход.

## 1. SQL-запрос вместо агентного цикла для задач по таблицам

**Статус:** не проверено. **Модуль:** М2 (решение задач). **Автор:** xz xz, 10 ноября.

### Суть

Модель получает схему таблицы и вопрос и пишет один SQL-запрос. Харнесс выполняет его и записывает результат в `answer.txt`.

### Откуда экономия

Сейчас задача по таблице стоит около 304 токенов за 3 вызова (прогон на прокси, `docs/gaps.md`):

1. модель смотрит файл (`head`);
2. пишет вычисление;
3. отдельным вызовом повторяет число из вывода.

Предложение убирает первый и третий вызовы:

- **данные в промпте:** заголовок, 2–3 строки и уникальные значения коротких колонок;
- **результат и есть ответ:** без ещё одного вызова модели.

Оценка: один вызов примерно на 250 входных и 40 выходных токенов, около 65 токенов, в 4–5 раз дешевле. **Это оценка, а не замер.**

Те же два приёма работают и с однострочником на Python. SQL — удобная и более безопасная форма, а не источник выгоды.

### Реализация

- Писать интерпретатор не нужно: `sqlite3` есть в стандартной библиотеке, `duckdb` (около 50 МБ в образе) читает CSV напрямую и сам определяет типы.
- Оформить как штатный инструмент `sql` с коротким описанием для `ReActAgent`: организаторы ждут агента («идея в том что делаете агента»).
- SQL не может читать файлы или запускать команды, а это плюс для LLM-проверки безопасности образа.

### Риски

| Риск | Что делать |
| --- | --- |
| Модель не видит данные целиком: `'widget'` против `'Widget'`, месяцы словами | уникальные значения коротких колонок в промпте |
| Ошибка в запросе | второй вызов с текстом ошибки |
| Финальные задачи «сильно отличаются»: несколько файлов, грязные данные | JOIN и приведение типов в SQL; запасной путь через обычного агента |
| Точность ниже текущей | баллы важнее токенов: при падении точности не внедрять |

### Масштаб

Задачи по таблицам — около 25%. При экономии примерно 240 токенов на задачу это около 6000 токенов на 100 задач, или 6% бюджета.

### Расширение

Тот же приём для поиска: базу знаний `kb/` превратить в таблицу фактов `(сущность, поле, значение)`, а цепочки вроде «работодатель наставника» находить через JOIN.

### Как проверить

1. Прототип: инструмент `sql` и промпт со схемой.
2. Набор задач по таблицам с новыми формулировками, включая регистр, несколько условий и невыполнимые случаи.
3. Сравнить с текущим агентом на одних задачах: точность, токены на задачу, число вызовов.
4. Внедрять, только если точность не ниже.

Оценка времени: прототип с замером на прокси — 1–2 часа.

## 2. Проверка противоречивости тестов в coding без LLM

**Статус:** не проверено. **Модуль:** М2 (решение задач), выбор задач — М3. **Автор:** xz xz, 10 ноября.

### Суть

До вызова модели найти `coding`-задачи, тесты которых нельзя пройти никаким кодом, и не тратить на них токены.

В общем случае это невозможно: «существует ли код, проходящий тесты» — алгоритмически неразрешимый вопрос. Но простые и самые вероятные виды противоречий ловятся дёшево.

### Что ловится надёжно

Функция без состояния не может вернуть разные результаты на одних и тех же аргументах. Собираем пары «вызов → ожидание» и ищем:

- один вызов с одинаковыми аргументами и разными ожиданиями в `assertEqual`;
- `assertEqual` и `assertRaises` на одних аргументах;
- `assertEqual(f(x), 3)` и `assertNotEqual(f(x), 3)`;
- `assertIsInstance(f(x), str)` при ожидаемом числе.

Ожидания сравниваем как значения (`ast.literal_eval`, `==`), а не как текст: `assertEqual(1, 1.0)` проходит.

### Реализация

Разбор текста тестов (AST) ломается, когда аргументы строятся в цикле или через переменные. Надёжнее **прогон с записью**:

1. Подменить функции `mylib` заглушками, которые запоминают аргументы и возвращают метку вызова.
2. Подменить `assertEqual` и другие проверки, чтобы они записывали пару «метка → ожидание» и не падали.
3. Один прогон тестов за доли секунды даёт все пары, как бы ни был написан тест.

Отдельно и тоже дёшево проверяется невыполнимость другого рода: нет файла с данными, тест импортирует несуществующий модуль.

### Что не ловится

- неравенства: `f(x) > 5` вместе с `f(x) == 3` требуют решателя ограничений;
- связи между функциями: `f(x) == g(x)` вместе с отдельными ожиданиями для каждой;
- состояние: классы, изменяемые аргументы, случайность, время.

### Ценность и риски

| Пункт | Оценка |
| --- | --- |
| Что даёт | только экономию токенов: штрафа за неверный ответ нет, наград за невыполнимые нет |
| Выгода | около 1000 токенов на каждую пойманную задачу: `coding` самый дорогой тип (977 против 173–366 у остальных на прокси) |
| Главный риск | ложное срабатывание: решаемая задача потеряна, а баллы важнее токенов |
| Правило | помечать только доказанное противоречие, при сомнении отдавать агенту |
| Неизвестно | как устроены невыполнимые `coding`-задачи в финале: в примерах их нет |

### Известная ошибка в старом коде

В прежнем харнессе (`harness/solvers/coding_solver.py`, функция `_contradictory`) ожидания сравниваются как текст через `ast.dump`, поэтому `1` и `1.0` считаются противоречием. Это ложное срабатывание. Результат «5 из 5» на сгенерированном наборе ничего не доказывает: противоречия там создавались тем же автором и ровно такого вида.

### Как проверить

1. Прототип проверки с прогоном и записью.
2. Набор: решаемые задачи с хитрыми, но совместимыми тестами (`1` и `1.0`, аргументы из цикла, `assertAlmostEqual`) и противоречивые задачи разных видов.
3. Главная метрика — **ноль ложных срабатываний** на решаемых задачах. Вторая — доля пойманных противоречивых.
4. Внедрять, только если ложных срабатываний нет.

Оценка времени: прототип с набором проверок — 1–2 часа.

## 3. Локальные модели в контейнере

**Статус:** не проверено. **Модули:** М1 (образ и запуск), М2 и М3 (использование). **Автор:** xz xz, 10 ноября.

### Основание

Организаторы разрешили запускать локально всё, что получится (`rules.md`). Регламент в этом пункте устарел.

### Ограничения

| Ограничение | Значение |
| --- | --- |
| Размер образа | лимит 4 ГБ, сейчас 1,36 ГБ: запас около 2,6 ГБ |
| Сборка | до 1000 с; `torch` её заметно удлиняет, `onnxruntime` легче |
| Запуск | только CPU, 8 ядер, 16 ГБ, 1 час на весь прогон; скачивать при запуске нельзя, веса кладём в образ |
| Безопасность | образ проверяет LLM; большие бинарные файлы описать в README |

### Вариант А: энкодер

Небольшая модель, которая превращает текст в вектор (эмбеддинг): похожие по смыслу тексты оказываются рядом. Размер — от 20 до 500 МБ, на CPU миллисекунды на текст.

Применения без обучения:

- **поиск по `kb/`:** найти нужные файлы по смыслу вопроса и положить их в промпт, экономя шаги агента;
- **похожие задачи:** взять реальную стоимость похожих задач, уже решённых в этом прогоне, как оценку для выбора задач.

Применения с обучением: предсказывать стоимость и невыполнимость по условию. Данных для этого пока мало: 8 примеров и собственный генератор.

Альтернатива без нейросетей: простые признаки (тип, длина условия, размер данных, число тестов) плюс регрессия или бустинг.

### Вариант Б: локальная генеративная модель

Маленькая модель вроде Qwen2.5 на 0,5–1,5 млрд параметров: в сжатом виде 0,4–1 ГБ, на 8 ядрах порядка 10–20 токенов в секунду. Её токены не идут через прокси и **не тратят бюджет**. openJiuwen подключается к ней так же, как к прокси, через совместимый с OpenAI сервер.

| Пункт | Оценка |
| --- | --- |
| Плюс | простые задачи бесплатно, бюджет прокси уходит на сложные |
| Качество | заметно слабее модели прокси: нужна проверка ответа или запасной путь через прокси |
| Время | генерация на CPU медленная, а на всё 1 час |
| Главный риск | обходит бюджет токенов, который и есть предмет конкурса |
| Условие | внедрять только после письменного подтверждения организаторов именно про генеративную модель |

Цифры размера и скорости — оценка, не замер.

### Как проверить

1. Получить письменное подтверждение про вариант Б.
2. Собрать образ с выбранной моделью и проверить размер, время сборки и работу под флагами конкурса.
3. Замерить скорость и точность на наборе задач, сравнить с моделью прокси.
4. Внедрять, только если баллы не падают, а время укладывается в час.

## 4. Оценка задач до решения

**Статус:** частично есть в прежнем харнессе (`harness/planner/`), в `agent-develop` нет. **Модуль:** М3 (выбор задач), признаки — М2. **Автор:** xz xz, 10 ноября.

### Что оцениваем

- **P(решу)** — шанс правильного ответа;
- **E[стоимость]** — сколько токенов уйдёт;
- **P(невыполнима)** — чтобы не начинать.

Приоритет задачи: `награда × P(решу) / E[стоимость]`.

### Направления, от дешёвых к дорогим

| № | Направление | Что даёт | Цена | Ограничение |
| --- | --- | --- | --- | --- |
| 1 | Разбор задачи без модели | признаки и невыполнимость | 0 токенов | только для понятных форм условия |
| 2 | Подсчёт входа токенизатором | почти точная входная стоимость | 0 токенов | выход и число шагов неизвестны |
| 3 | Обучение внутри прогона | уточнение оценок по типам | 0 токенов | первые задачи каждого типа идут вслепую |
| 4 | Классическая модель по траекториям | P(решу) и стоимость по признакам | токены на сбор данных | нужны сотни прогонов |
| 5 | Похожие задачи через энкодер | стоимость по похожим решённым | 0 токенов прокси | см. идею 3 |
| 6 | Пробный шаг и лимит на задачу | оценка по факту, остановка убыточных | токены одного шага | это не оценка заранее |
| 7 | Распределение бюджета | порядок задач | 0 токенов | качество зависит от оценок 1–6 |

### Подробности

**1. Разбор без модели.** Сигналы по типам:

- **coding:** сколько видимых тестов падает и с какими ошибками (их можно просто запустить), размер файла, число функций, противоречивость тестов (идея 2);
- **data_analysis:** число строк и колонок, число условий в вопросе, есть ли упомянутые колонки и значения;
- **search:** длина цепочки («работодатель наставника» — два шага), есть ли упомянутые сущности в `kb/`;
- **math:** число операций в условии.

**2. Токенизатор.** Промпт, описания инструментов и данные, которые пойдут в запрос, известны заранее. tiktoken или токенизатор Qwen дают входную стоимость почти точно.

**3. Обучение внутри прогона.** Стартовые оценки по типу уточняются после каждой задачи, например скользящим средним. Это рамка «многорукого бандита»: попробовать по несколько задач каждого типа, затем тратить бюджет на выгодные. Не требует данных заранее, поэтому устойчиво к тому, что финальные задачи «сильно отличаются».

**4. Классическая модель.** Признаки из пункта 1, реальная стоимость и результат из наших прогонов, регрессия или бустинг. Регламент это прямо разрешает.

**5. Энкодер.** Эмбеддинг условия, поиск похожих среди решённых, их фактическая стоимость. Полезно, когда признаки из пункта 1 не описывают задачу.

**6. Пробный шаг.** По первому шагу агента решить, продолжать ли. Сюда же лимит на задачу: остановиться, когда стоимость явно превысила ожидаемую. Спросить саму модель о сложности возможно, но это стоит токенов и обычно ненадёжно.

**7. Распределение бюджета.** Задача о рюкзаке: брать по убыванию приоритета, пока хватает бюджета, с поправкой на разброс стоимости. Штрафа за неверный ответ нет, поэтому при остатке бюджета разумно браться и за сомнительные задачи.

### Что успеть до 13 ноября

- **Обязательно:** 1, 2, 3 и 7 — дёшево, без обучающих данных, устойчиво к новым формулировкам.
- **Если хватит времени:** 4 на траекториях из наших прогонов.
- **Позже:** 5; из 6 — только лимит на задачу.

### Как проверить

1. Набор задач с новыми формулировками и случайными наградами, независимыми от сложности.
2. Сравнить при одинаковом бюджете: порядок по каталогу, сортировка только по награде, приоритет по оценкам.
3. Метрики: сумма баллов, затем расход; отдельно — ошибка оценки стоимости по типам.
