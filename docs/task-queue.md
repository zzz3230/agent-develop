# AGE-12: простая очередь выгодных задач

11 ноября 2026. Поверх существующего `run_agent.py` добавлена минимальная
политика порядка задач. Агент, модель, инструменты и лимиты попытки не менялись.

## Как работает

`runtime/task_queue.py`, около 150 строк, без внешних зависимостей.

- Оценка задачи: `reward × p(тип) / c(тип)`.
  `p` — доля решённых попыток этого типа в текущем запуске, `c` — средний
  фактический расход попытки этого типа. Обе величины считаются только по
  наблюдаемым исходам самого харнесса (ответ сохранён, coding прошёл тесты),
  эталоны не используются.
- Априорные значения нейтральные и не подогнаны под бенчмарк: `p = 0.5` с весом
  2 псевдопопытки, `c = (стартовый + потолочный лимит стоимости профиля) / 2`
  с весом 1. Профили берутся из `runtime/attempt_policy.py`.
- Если известна оценка остатка бюджета, сначала выбираются задачи, чья
  ожидаемая стоимость в остаток помещается. Глобальную остановку по-прежнему
  делает прокси; локальная оценка ничего не прерывает.
- `QUEUE=0` — исходный порядок каталогов (база). По умолчанию `QUEUE=1`.
- `RETRY=1` (по умолчанию выключено) — не более одного повтора задачи и только
  если: первая попытка остановлена лимитом (а не ошибкой формата или API),
  повтор с лимитом на потолке профиля помещается в остаток, а его оценка
  `reward × p × 0.3 / c_потолок` не хуже лучшей ещё не начатой задачи.
- В журнал пишутся события `queue` (режим) и `queue_pick` (задача, оценка,
  повтор или нет), исход задачи содержит признак `retry`.

## Замер

Живого ключа прокси в этой среде не было, поэтому новый реальный прогон не
делался. Замер — воспроизведение записанных реальных попыток из
`docs/benchmarks/stock-oj-100` (100 условий, 80 выполнимых, 421 балл): для
каждой задачи берутся её фактический расход, время и итог, а затем
моделируется порядок и бюджет. База — записанный порядок и ещё 200 случайных
перестановок каталога. Команда:

```bash
python evaluation/replay_queue.py \
  --graded docs/benchmarks/stock-oj-100/ours-graded.json docs/benchmarks/stock-oj-100/stock-graded.json \
  --output docs/benchmarks/stock-oj-100/queue-replay.json
```

Наш рабочий агент (`ours-graded.json`):

| Бюджет | База, средние баллы по 201 порядку | Очередь, средние баллы | Минимум база / очередь | Очередь лучше / равно / хуже | Время база / очередь, с |
|---|---:|---:|---:|---:|---:|
| 30000 | 60.1 | 131.7 | 4 / 123 | 201 / 0 / 0 | 271 / 311 |
| 50000 | 100.0 | 172.0 | 35 / 157 | 200 / 0 / 1 | 460 / 484 |
| 100000 | 202.4 | 259.3 | 126 / 248 | 198 / 1 / 2 | 934 / 953 |
| 150000 | 306.0 | 306.0 | 306 / 306 | 0 / 201 / 0 | 1421 / 1421 |

При бюджете 100000 в записанном порядке база набрала 209 баллов, очередь — 263.
Если очередь не знает остаток бюджета, она даёт 259.0 в среднем (199 / 1 / 1).
При 150000 помещаются все задачи, поэтому порядок не важен — это ожидаемо.

Для штатного OJ (`stock-graded.json`) при 100000: база 33.7 в среднем, очередь 74.0,
201 / 0 / 0. Политика помогает и слабому агенту, потому что быстрее находит
выгодный тип (у штатного OJ это математика).

## Повторы

Повторы реализованы, но выключены: в записанных данных нет второй попытки
одной и той же задачи, поэтому выигрыш от повтора измерить нельзя. Включать
`RETRY=1` стоит только после живого замера на dev-наборе
(`docs/suite-v2.md`) с одинаковым бюджетом.

## Ограничения

- Воспроизведение предполагает, что расход и итог задачи не зависят от
  порядка. Это верно для независимых сессий одной модели при temperature=0,
  но не учитывает обрыв задачи, пересекающей границу бюджета.
- Корпус синтетический и на нём не настраивали политику; априорные значения
  взяты из лимитов профиля.
- Окончательная проверка — живой прогон `evaluation/compare_changes.py --only base +queue`
  на одном наборе и бюджете.
