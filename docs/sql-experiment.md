## Устройство

CSV загружаются в SQLite в памяти. Все столбцы TEXT, чтобы не терять ведущие нули и не угадывать денежные типы. В промпт передаются имена таблиц и колонок, число строк, две примерные строки, короткие множества значений. Для денег доступны DEC_MUL, DEC_SUB и CENTS с Decimal/HALF_UP. SQL разрешён только для чтения; результат должен быть одной непустой ячейкой. Ошибка или неоднозначный результат возвращаются агенту.

Команда `python3 -m runtime.sql_tables --query "SQL" --final` явно помечает ответ. Штатный AFTER_TOOL_CALL rail вызывает request_force_finish: отдельное обращение к модели для повтора числа не требуется. Без --final запрос считается пробным. Сам факт успешного SQL не доказывает, что запрос правильно решает условие.

## Применение

Вывод: SQL полезен как быстрый путь для агрегатов — на трёх простых
задачах он дал 6/6 и среднюю стоимость 151–183 вместо 268–332 у обычного
Python. Но задачу с последовательной обработкой событий SQL не решил
оба раза: один раз закончились шаги, другой раз получен неверный скаляр.
Успешное выполнение запроса не проверяет его смысл.

На данном наборе лучший общий вариант — python_schema: 12/12 и на
40.9% меньший суммарный расход относительно обычного Python. Эти
результаты не достаточны для массового переключения неизвестных задач
на SQL. Обе дополнительные схемы оставлены opt-in, базовый режим сохранён.

`CSV_SCHEMA=1` передаёт ту же схему обычному агенту, сохраняя Python-путь.
`CSV_SQL=1` включает SQL-путь; при обоих флагах приоритет у SQL.
Для обоих режимов max_output=1200; стандартный режим сохраняет 600.
Схема более 12000 символов или ошибка чтения/загрузки возвращает обычный
режим до запроса к модели. Пределы общего бюджета, шагов и времени не
повышаются. В SQLite денежные вычисления выполняются через Decimal-helpers,
а не через REAL.

Локальная команда для простого SQL-теста:

```powershell
powershell -ExecutionPolicy Bypass -File "C:\Users\hilis\hackathon-task\test-proxy.ps1" -TaskId data_analysis_0002 -Sql -Image agent-develop:m2-sql
```

Для схемы с Python вместо `-Sql` передать `-Schema`. Локальный образ
`agent-develop:m2-sql` собран с рабочим entrypoint и обоими режимами.

Дополнительные проверки реального entrypoint, вне сравнительной таблицы:
SQL на data_analysis_0002 → 158, 1 вызов, 150.6 стоимости, run
20261110-204853-324. CSV_SCHEMA на hard_csv_revenue → 659623, 3 вызова,
767.6 стоимости, run 20261110-204853-299. Ответы совпадают с эталонами;
finish в обоих журналах — all tasks handled. Это проверки под рабочими
лимитами 2500 на задачу. Все файлы и журналы сохранены вне репозитория.

Эксперимент подключён к рабочему entrypoint флагом CSV_SQL=1; по умолчанию выключен. Для data_analysis добавляется схема, SQL_SYSTEM и SqlCompletionRail. Неподдерживаемая схема возвращает обычный путь до вызова модели; ошибка SQL видна агенту, который может исправить запрос или перейти к Python. Для SQL-профиля max_output=1200, общие лимиты времени/шагов/стоимости production не увеличены.

## Ограничения и разработческие прогоны

По два повтора на задачу — первичная проверка, не доказательство стабильности на финале. В предыдущем варианте модель часто игнорировала SQL-инструкцию, затем обнаружено преждевременное завершение по пробному COUNT(*). Эти два варианта остановлены и исправлены до основного сравнения; их расходы не включены в таблицу. Они сохранены отдельно в sql-ab и sql-ab2. В sql-preflight* — дополнительные пробные запуски для настройки CLI и native rail. Все эти расходы реальны и не являются экономией рабочего решения.

Основная серия: 100 запросов, расход 20836.1; оценочный usage у 0 попыток.

С учётом пробных и остановленных разработческих вариантов суммарный
расход benchmark-запусков этого эксперимента — 45718.7. Ещё 918.2 по
журналам рабочего entrypoint ушло на две интеграционные проверки. Полная
сумма журналов — 46636.9; счётчик entrypoint может применять оценку по
символам поверх usage, поэтому это не независимый биллинг прокси.
