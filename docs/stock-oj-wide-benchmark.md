# OJ с большим лимитом и рабочими файловыми инструментами

Базовый ReActAgent получает 100 итераций на задачу, до 8192 выходных токенов на один ответ модели и до 600 секунд на задачу. На весь прогон — 3300 секунд; остаток общего времени ограничивает и уже начатую задачу. Отдельного локального ограничения стоимости задачи у OJ нет. Общий бюджет контролирует прокси, локальная сумма 100000 информационная. Настройки вынесены в аргументы `evaluation/compare_stock.py`; конфигурация и версии зависимостей сохраняются в config.json. Возобновление с другими настройками запрещено.

Пустой дополнительный системный промпт и шесть штатных инструментов оставлены прежними. Наш вариант использует прежние профили и ограничители, включая bash, схемы CSV и контекст поиска. Модель для обоих — qwen3.8-27b-noreason, temperature=0. Код производственного алгоритма не меняется. Это сравнение конфигураций ReActAgent; DeepAgent здесь не измеряется.

## Почему пришлось исправить среду

Первый запуск с 100 итерациями на прежней зависимости filelock 4.2.9 остановлен после воспроизведения ошибки файловых инструментов. В первой задаче он всё-таки вычислил правильный ответ, но затратил 332,9 секунды: большая часть времени ушла на ожидание блокировки файла.

Причина установлена по установленным исходникам и проверке без модели: OJ HybridAsyncReadWriteLock создаёт отдельные asyncio tasks для acquire и release. В filelock 4.2.9 блокировка принадлежит конкретной task; освобождение из другой task вызывает `Cannot release a lock ... that is not held by this task through this wrapper`. После неудачного освобождения write lock возникает также `Cannot close an active file lock`, последующие обращения могут ждать внутреннего таймаута 300 секунд.

В метаданных OJ 0.1.19 указана зависимость filelock >=3.25.0. Версия 3.25.0 проходит независимую проверку последовательности read → write → edit → read штатными инструментами. Версия 4.2.9 падает на первом read. Проверка: `evaluation/check_stock_io.py`, без LLM, сети и эталонных ответов. Контрольный образ `evaluation/Dockerfile.stock-io` закрепляет совместимую версию. Оба новых сравниваемых варианта запускаются в одном этом образе. Совместимая версия также закреплена в основном requirements.lock; код профилей и контроллера не изменён.

Сборка: сначала `docker build -t agent-develop:stock-wide .`, затем `docker build -f evaluation/Dockerfile.stock-io -t agent-develop:stock-wide-io .`. Для воспроизведения ошибки можно собрать контрольный образ с `--build-arg FILELOCK_VERSION=4.2.9`. Параметры запуска сравнения: `--stock-steps 100 --stock-output-tokens 8192 --stock-task-seconds 600 --run-seconds 3300`. Они сохраняются вместе с результатами; теперь это также значения по умолчанию для базового варианта.

Исходный диагностический запуск и его затраты хранятся отдельно и не входят в новое сравнение. Смена зависимости не скрывается как эффект увеличения числа шагов: исправление среды и увеличение лимитов выполнены одновременно, их отдельный вклад здесь не изолируется.

## Данные и проверка

Те же окончательные 100 заданий: 80 разрешимых и 20 неразрешимых, 25 каждого типа; максимальная награда 421. SHA-256 входного дерева: `fc09a24fabfe846c3b2bab888887cb6bc2026cc2720feec5304bcf5062c55163`. Набор основан на 16 разрешимых семействах по пять вариантов; он не калиброван под закрытую выборку конкурса.

Входы примонтированы только для чтения, рабочие копии и результаты у каждого агента отдельные. Эталоны и генератор не входят в контейнер. В кодовых задачах исходные видимые и дополнительные тесты проверяются после прогона отдельно, без сети. Ожидаемые ответы не используются агентом и контроллером. Неразрешимые задания не приносят баллов, правильные отказы учитываются отдельно.

Точная стоимость — input / 10 + output по usage прокси. Расчётный срез до 100000 учитывает только целиком завершённые задачи в том же порядке; это не реальный прогон с отключением прокси в середине ответа. При достижении общего времени публикуются число обработанных и список необработанных задач, без выдачи частичного прогона за 100 завершённых попыток.
